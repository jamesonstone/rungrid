# SPEC

## PURPOSE

Give a running multi-repository workspace one repeatable command that picks
up merged changes in place. Today the operator runs `rungrid sync`, then
manual `npm ci` and `go` steps, then `rungrid down` and `rungrid up`. A merged
npm dependency (for example a new Expo native module) breaks the frontend
until all of that happens. `rungrid update` must be as safe to repeat as
`npm i`: a run with nothing new runs nothing and restarts nothing.

## CONTEXT

- `rungrid sync` already fast-forwards default branches with an expected-OID,
  fail-closed contract, and pauses every running service in the default
  worktree around the file change. It does not install dependencies and it
  restarts a hot-reloading server that did not need it.
- With an active runtime, `sync` runs as a disabled Process Compose
  maintenance job compiled into the generation. A runtime generated by an
  older binary has no job for a new operation.
- `MaintenanceCoordinator` owns the exact pause and resume path for workspace
  processes and cooperative tab sessions. The `maintenance` package cannot
  import `override` (import cycle), so service resolution stays in
  `lifecycle`.
- `workspace.Execute` already runs lifecycle hooks with resolved environment,
  process-group timeout, and private redacted logs.

## REQUIREMENTS

- New top-level `rungrid update` in the Maintain help section, with
  `--repository` (repeatable), `--dry-run`, `--baseline`, and `--json`
  (`rungrid/output/v1`, kind `WorkspaceUpdateReport`).
- Per repository: inspect and fast-forward exactly as `sync` does. Never reset,
  stash, rebase, or touch a missing, ahead, diverged, dirty, or unavailable
  default branch; report it SKIPPED with the reason. A current default
  checkout must also be clean before anything runs in it.
- Dependency installs run only when their inputs changed since the last
  successful run: `go mod download` (never `go mod tidy`) for `go.mod`/`go.sum`;
  `npm ci`, `pnpm install --frozen-lockfile`, or `yarn install
  --frozen-lockfile`/`--immutable` for the lockfile plus `package.json`.
- Post-update steps are declared per service in `.rungrid.yaml`
  (`refresh.steps` with argv and watched paths) and run only when their watched
  paths changed. Detection supplies defaults only.
- Restart only affected running services through the existing Process Compose
  lifecycle. Hot-reloading servers keep running unless their dependencies were
  reinstalled.
- Per-repository, per-unit, and per-service status: UPDATED, CURRENT, SKIPPED
  with a reason, or FAILED.
- One repository's failure does not stop others, and every paused service is
  resumed.
- Change-detection fingerprints live in the project state directory.

### Non-goals

- Updating feature, override, or selected worktrees.
- Modifying consumer repositories or guessing project-specific steps such as
  migrations from project type.
- Overview visibility for update runs (see DECISIONS).

## ACCEPTED PLAN

1. Add the optional `refresh` block to the service schema, types, and
   validation.
2. Export `InspectDefault`, `FastForward`, and `CleanWorktree` from
   `maintenance` without changing `sync` behavior.
3. Add `internal/update`: committed-tree fingerprints, dependency and
   hot-reload detection, a planner, an apply engine, a state store, and a
   human renderer.
4. Add `lifecycle.UpdateCoordinator` that resolves effective checkouts and
   reuses the maintenance pause/resume path for exact named services.
5. Wire `rungrid update`, help golden, README, CLI specification, and agent
   instructions.
6. Validate with real temporary Git remotes, a headless smoke, a live Process
   Compose smoke, and a read-only dry run against a real workspace.

## DECISIONS

- **New command, not a `sync` flag.** `sync` is a narrow Git contract reused by
  `up --sync`, `worktrees update --sync`, and `reconcile`, and its report kind
  is `RepositorySyncReport`. Update adds installs, steps, and restart policy
  with its own report. A flag would change what `sync` means for those
  callers. `update` reuses the sync inspection and fast-forward primitives, so
  the Git safety contract is identical.
- **Plan before the file change, then pause only what restarts.** The planner
  fingerprints the target commit (after fetch) before fast-forwarding, so
  exactly the services that need a restart pause before files change, and
  everything else, including hot-reloading servers, keeps running. This
  narrows the `sync` rule "pause every service in the default worktree".
- **Fingerprints hash committed blobs (`git ls-tree -r`), not files on disk.**
  They are deterministic, ignore modification times and ignored build output,
  allow planning against the remote commit without a checkout, and are exact
  because the checkout must be clean.
- **Unknown means run, for installs and steps.** With no recorded fingerprint,
  an install or step runs, like `npm i` on a fresh checkout. A service with no
  recorded watch fingerprint compares against the pre-fast-forward commit, so a
  first run does not restart services for code that was already running.
  `--baseline` adopts an already-prepared workspace without running anything.
- **Record only success.** Units and restarts record new fingerprints only
  after they succeed. The first failed unit skips the repository's remaining
  units, paused services still resume, and the next run retries.
- **Run in the CLI process under the maintenance lock, not as a Process
  Compose job.** A job would need a new generation, so `update` would fail
  against every runtime started before upgrading, which is the exact case this
  command is for. The CLI holds the same project lock the maintenance worker
  uses and drives the same supervisor and session pause path. Overview does
  not show update runs; logs live under `lifecycle-logs/update/`.
- **Restart policy names behavior, not tools.** `changed`, `dependencies`, and
  `never`. Detection of common hot-reloading servers only selects the default.
- **Compose defaults are conservative.** Compose services install nothing and
  watch only their Compose file.

- **Two restart paths, chosen at plan time (#66).** A tab service with a live
  session restarts through that session, which keeps the tab and its log view.
  A running tab service whose session ended restarts through Process Compose,
  which is its current state. The planner records the path, so the dry run
  predicts how each service restarts. Refusing such a service was rejected:
  it is the normal state after a Warp tab closes or a session exits.
- **Pause one service at a time and roll back (#66).** The engine pauses in
  reverse manifest order and, if one pause fails, restores every service it
  already paused before reporting FAILED with nothing changed. Each resume has
  its own recovery deadline, and one failed resume does not skip the others.

- **Session restarts fall back to Process Compose (#70).** A failed or
  unresponsive session pause, or a failed session resume, no longer ends the
  restart. The service is stopped or adopted and started through Process
  Compose, and the report names the fallback. The fallback is a small
  state machine (`serviceRestart`) tested against a fake Process Compose.

## DISCOVERIES

- `npm ci` on a package with no dependencies does not create `node_modules`.
  An unconditional "node_modules missing" rule therefore reran `npm ci` on
  every run. The rule now applies only when `package.json` declares
  dependencies. Found by the headless smoke.
- On a real Warp workspace a tab service can run with only its managed tab
  shell and no session registration. The first release paused all services
  through one coordinator call that required a session, so one such service
  failed the whole repository (#66).
- Process Compose reports readiness as `Ready`, but the session resume check
  and `waitForService` required the word `healthy`. A resumed service with a
  health check therefore never became ready. After the startup timeout the
  session failed the resume and stopped the process, so the frontend ended
  `Completed`. This also affected `sync`. One `processcompose.HealthReady`
  predicate now serves all readiness checks, and `Not Ready` is no longer
  read as ready during `up`.
- Process Compose `stop` returns at once and leaves the process `Terminating`
  until its tree exits (seconds for `make` running Air), and a `start` sent in
  that window returns HTTP 400 "already running". The session acknowledged a
  pause right after the stop request, so a fast resume (no install to run) failed.
  The session then left backend `Completed`, and worker, which depends on a
  healthy backend, was `Skipped` (#70). Every pause now waits until the process
  has settled, and every start waits for a settled process or adopts a running
  one.
- A session runs the binary that started its tab. Workspaces whose tabs were
  opened by an older build keep the old resume behavior until `down` and `up`.
- A service whose working directory is the repository root watches the whole
  repository by default, so any merge restarts it. Such services should
  declare `refresh.watch`.
- Lifecycle logs are keyed by run-local index and name, so each run overwrites
  the previous run's log for the same unit. This keeps the directory bounded.

## VALIDATION

- `make check`: fmt-check, vet, test, test-race, sanitize, license, compile,
  build-cross. PASS.
- `make lint`: 0 issues. `make vuln`: no vulnerabilities found.
- `kit check 0002-workspace-update`: PASS. `kit check --project` still reports
  three pre-existing Kit contract-block drift findings that also fail on `main`.
- `internal/update` tests use real temporary Git remotes with a fake
  coordinator and executor: first run installs and second run is a no-op;
  each changed input runs only its unit and restarts only its service, then a
  repeat is a no-op; dirty checkout is skipped untouched; dry run changes no
  ref, state, process, or command; a failed install resumes services and is
  retried; one repository's failure does not stop another. Detection tests
  cover globs, fingerprints, nested Go modules, pnpm, yarn berry, hot-reload
  detection, Compose defaults, and the `node_modules` rule. Manifest tests
  cover `refresh` validation.
- Headless smoke (temporary remote, real `npm ci`, `go mod download`, and a
  step): fast-forward, step ran only after its watched path changed, rerun
  CURRENT, JSON envelope correct, state at `update/inputs.json`.
- Live Process Compose smoke: a web source change left the hot-reload service
  on the same PID while the API restarted on a new PID; a lockfile change ran
  only `npm ci` and restarted only web; reruns were CURRENT.
- Read-only `rungrid update --dry-run` against a real running workspace
  produced the expected plan without fetching or writing state.
- #66 smoke (Process Compose, three tab services: two with live sessions, one
  whose session was killed): the merged build reproduced the pause failure.
  The fix restarted all three, kept both sessions alive, and a repeat run was
  CURRENT. A dry run reported `session` and `process-compose` paths correctly.
- #66 real workspace (10 services, 3 tab sessions): after `down` and `up` on
  the fixed build, the dry run predicted session restarts for backend, worker,
  and frontend. The real run installed Go and npm dependencies and restarted
  all three through their sessions (1m40s, exit 0). The second run reported
  CURRENT everywhere with unchanged PIDs, and all 10 services stayed
  Running/Ready.
- #70 smoke (Process Compose, a slow-stopping health-checked service with a
  dependent): the merged build reproduced `start process returned HTTP 400`
  with the services left `Completed` and `Skipped`. With the fix both
  restarted through their sessions. With the session frozen (SIGSTOP) the pause
  timed out, the restart fell back to Process Compose, the thawed session
  stayed alive without stopping the process, and no maintenance files were
  left.
- #70 real workspace: after `down` and `up` on the fixed build, the pending
  backend (session, Air) and worker (no session, Process Compose) restarts
  that had failed both succeeded (exit 0, 18s). The second run was CURRENT
  with unchanged PIDs, and all 10 services were Running/Ready.
- #66 unit test: a pause failure restores the already-paused service, moves no
  ref, runs no unit, records nothing; the retry succeeds; the next run is
  CURRENT.

## OUTCOME

`rungrid update` is implemented as planned. Remaining risks: Overview does not
show update runs; restart scope depends on accurate `refresh.watch` for
services rooted at a repository root; services backed by checkouts outside
declared repositories (for example a sibling repository reached through a
script) are not fetched unless that repository is declared.
